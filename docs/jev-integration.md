# Jev（TypeSafe System One）活用ガイド — 適用手順と下流プロジェクト別の活用パターン

> **このファイルは「Jev を本ベースおよび下流プロジェクトでどう使うか」の唯一の正本（SSOT）である。**
> 判断基準（向き不向き・ガードレール）はここに置き、コードは `tools/jev_client.py`（共通クライアント）と
> `tools/triage_notification.py`（ベース側の 1 適用）が実装する。下流プロジェクトは本ガイドの §4 を
> 自分のドメインに読み替えて、活用箇所を自分で決める。

> 一次情報: [docs.typesafe.ai](https://docs.typesafe.ai)（API 契約・モデル・料金・既知の弱点は
> ライブドキュメントが正本。本ファイルの数値は 2026-09-17 時点）。

## 0. 30 秒で分かる Jev

Jev は TypeSafe が 2026-09-15 に早期アクセス公開した **System One モデル**。テキストを生成せず、
`state`（文字列 / JSON）に対する **型付きの判断と確率だけを返す**。1 リクエストに複数の質問を詰めると
並列に評価され、キャリブレーション（確率と実際の的中率の一致）を目的に学習されている。

| 項目 | 値（2026-09-17 時点） |
|---|---|
| エンドポイント | `POST https://api.typesafe.ai/v1/systemone`（`Authorization: Bearer <key>`） |
| モデル | `jev-1.13.0`（`jev-latest` / `jev-preview` は現在これを指すエイリアス） |
| 料金 | 入力 $0.042 / Mtok・**出力無料**（質問を増やしてもほぼ無料） |
| レイテンシ | 実測中央値 約 400 ms（公式は 70〜500 ms） |
| レート制限 | 250k tok/s・1,200 req/min（早期アクセス中は予告なく変動） |
| コンテキスト | state + 全質問で 64k tok / state + 最長質問で 32k tok |
| 入力 | テキストのみ（画像・音声は非対応）。日本語は実測で問題なし |
| データ方針 | 入力で学習しない・第三者非開示（プライバシーポリシー）。ZDR はエンタープライズ限定。米国ホスト |

3 つのプリミティブ（質問の型）:

| 型 | 返るもの | 使いどころ |
|---|---|---|
| **Choice** | 選択肢の確率分布 + `choice` + `confidence` | ルーティング・分類・候補からの選択 |
| **Noul** | Yes の確率 1 つ（`confidence` なし） | 条件判定・複数ラベルは 1 ラベル 1 Noul |
| **Score** | 順序尺度上の期待値 + 分布 + `confidence` | 程度の評価・ランキング用の比較可能スコア |

## 1. 向き不向き（採否の一次判定）

**向いている**（System One 的な「小さな意味判断」）:

- 正規表現・キーワード一致で書いている **意味判定の言い換え耐性を上げたい**（本ベースの適用例 §3）
- 「この通知は人間の判断が要るか」「この差分は認証境界に触れるか」のような **Yes / No + 確信度**
- 候補が有限集合のとき、**生成させずに選ばせる**（タイトル案の選択・担当スキルのルーティング）
- 同じ state に対して独立な質問を **まとめて 1 回で** 聞ける処理（1 質問あたりのコストがほぼゼロ）

**向いていない**（公式が jaggedness として明示する弱点。コードか生成モデルでやる）:

- **生成**（本文・説明・理由の文章化）。Jev は理由を返さないため、監査で説明が要る判断には単独で使わない
- **数値計算・カウント・日付比較**（「どちらが先か」「何件あるか」はコードで計算し、Jev には意味判断だけ渡す）
- **多段の間接参照・二重否定**（質問を分割して 1 ホップずつ問う）
- **無関係な情報が多い state**（差分全文を渡すと精度が落ちる。要約・抽出してから渡す）
- **敵対的テキストへの耐性が要る判断**（公式が改善途上と明記。§5 の非対称ルールで扱う）

迷ったら: 「答えが有限集合で、間違えても人間かコードが後段で受け止められるか？」→ Yes なら候補。

## 2. 有効化手順（共通）

Jev は **既定 OFF の opt-in**。`JEV_KEY` が無いセッションでは、本ベースのどの処理も Jev を呼ばず
従来どおり動く（下流に配布しても環境変数を入れるまで挙動は変わらない）。

1. API キーを取得する（[typesafe.ai](https://typesafe.ai) の早期アクセス。アカウント作業は A-6 相当で人間が実施）
2. 環境変数 **`JEV_KEY`** に設定する（`docs/rules/env-vars.md` の表に追記済み。Claude.ai の環境変数、
   または GitHub Variables 経由）。公式 SDK 互換の `TYPESAFE_API_KEY` でも可（`JEV_KEY` 優先）
3. 疎通を確認する:

```bash
python3 tools/jev_client.py --ping     # 認証と利用可能モデルを表示（キーの値は表示しない）
python3 tools/jev_client.py --demo     # 3 プリミティブのサンプル 1 リクエスト
python3 tools/triage_notification.py --self-test       # 決定論 28 件 + Jev 分岐のオフライン検証（モック・実 API なし）
python3 tools/triage_notification.py --self-test-jev   # ベース側 1 適用の実 API 検証（8 ケース・JEV_KEY 必須）
```

| 変数 | 既定 | 用途 |
|---|---|---|
| `JEV_KEY` | （未設定＝無効） | API キー。これが無ければ全処理が Jev なしで動く |
| `JEV_DISABLE` | 未設定 | `1` で一時的に無効化（キーを消さずに切り分けたいとき） |
| `JEV_MODEL` | `jev-1.13.0` | モデル ID。**エイリアス `jev-latest` は使わない**（新版で判定が黙って変わる。閾値を較正した実装ではピン留め） |
| `JEV_VERBOSE` | 未設定 | `1` で不通・HTTP エラーの理由を stderr に出す（既定は静かにフォールバック） |
| `JEV_TRIAGE_MIN_CONFIDENCE` | `0.85` | 通知トリアージで Jev の A 判定を採用する確信度の下限 |
| `JEV_TRIAGE_TIMEOUT` | `5.0` | 通知トリアージでの 1 リクエストのタイムアウト（秒） |
| `JEV_MAX_CONSECUTIVE_FAILURES` | `3` | この回数連続で失敗したら、同一プロセス内では以降の呼び出しを省略する（サーキットブレーカー・§2.1） |

**コードから使う**（`tools/` 配下のスクリプトは同ディレクトリ import で届く）:

```python
import jev_client

if jev_client.is_enabled():
    r = jev_client.system_one(
        {"text": text},                                   # 判断に必要な部分だけ
        {"is_urgent": {"type": "noul", "instructions": "`text` conveys urgency"}},
    )
    if r:                                                 # None なら不通。既存ロジックに倒す
        urgent = r["answers"]["is_urgent"]["noul"] >= 0.8
```

`system_one()` は **失敗時に例外を投げず `None` を返す**（fail-soft）。呼び出し側は必ず `None` の分岐で
Jev なしの既存動作に倒す。厳密にエラーを見たいときだけ `strict=True`。

### 2.1 Jev が使えないときのフォールバック（全適用箇所の共通契約）

Jev は **補完** であって前提ではない。どの適用箇所も「Jev なしで成立する既存ロジック」を残し、
Jev はそれに上乗せする。使えない状況は 4 種類あり、いずれもワークフローを止めない。

| 状況 | クライアントの挙動 | 呼び出し側の挙動 |
|---|---|---|
| キー未設定 / `JEV_DISABLE=1` | `is_enabled()` が False。API は呼ばない | 既存ロジックのみで動く（下流に配布した直後の既定状態） |
| 認証失敗（401）・検証失敗（422） | 再試行せず `None`。`JEV_VERBOSE=1` で理由を stderr | 既存ロジックの結果を採用。422 は質問設計の不備なので `--self-test-jev` で検出する |
| レート制限（429）・過負荷（529） | 指数バックオフで 1 回再試行 → それでも失敗なら `None` | 既存ロジックの結果を採用 |
| ネットワーク不通・タイムアウト・不正応答 | `None`。連続 3 回（`JEV_MAX_CONSECUTIVE_FAILURES`）で **サーキットブレーカーが開き**、同一プロセス内の以降の呼び出しは API を叩かずに即 `None` | 既存ロジックの結果を採用。バッチ処理（通知 N 件のトリアージ等）が不通時にタイムアウト × N で遅くならない |

- 判定結果には `jev` フィールド（照会したときだけ判定内容、それ以外は `null`）が入るので、
  ログから「Jev が効いたか / 倒れたか」を後から区別できる（`reason` も Jev 採用時だけ書き換わる）
- 通知トリアージでは、Jev が倒れたときの結果は **Jev 導入前とまったく同じ**（正規表現のみ）。
  「Jev が無いと @mention が減る / 増える」という非対称は無い（Jev は A を追加する方向にしか効かないため、
  倒れた分は「言い換えの取りこぼしが従来どおり残る」だけ）
- フック（同期実行）に組み込む場合は、この契約に加えてタイムアウトを短く（1〜2 秒）し、
  不通時の追加待ちが無人ルーティンの停止要因にならないことを先に検証する（§5 G-8）
- 実 API を使うセルフテスト（`--self-test-jev`）は、キー未設定なら skip（exit 0）、不通なら
  `unreachable` として skip する。CI を Jev の可用性に依存させない

## 3. 本ベースでの 1 適用: 通知トリアージの補完（`tools/triage_notification.py`）

`user-confirmation-minimization.md` の A-1〜A-6 を通知に機械適用する分類器は、これまで正規表現だけで
判定していた。正規表現は決定論的で速い反面、言い換え（「与信枠を使い切った」「4 周目に入った」）を
取りこぼし、語彙一致の偽陽性（「OAuth の解説記事を書いた」）を出す。

**構成（2 段・非対称）**:

```
通知テキスト + ラベル
  → ① 正規表現（従来どおり・決定論）
       ├─ A 判定 → 確定（Jev は呼ばない）
       └─ 非 A  → ② Jev に A-1〜A-6 の定義を state に同梱して Choice で問う（JEV_KEY があるときだけ）
                     ├─ A-x かつ confidence ≥ 0.85 → A に昇格（reason に Jev 判定を記録）
                     └─ none / 低確信度 / 不通       → ① の結果を維持
```

- **送信前の秘密検知ゲート（G-4 の実装）**: `tools/secret_scan.py` の内容ルール（コミット / push 経路と同じ
  検知器）を通し、トークン・鍵・認証情報の疑いがある通知は **Jev に送らず** 従来判定に倒す（redaction ではなく
  送信スキップ。検知器が読めないときも送らない fail-closed）。Issue / PR 本文に誤って貼られた秘密が
  第三者 API へ渡る経路を塞ぐ
- **Jev は A を追加する方向にだけ効く**。①が A と判定したものを Jev が取り消すことはない。
  通知本文は Issue / PR コメント等、外部の誰でも書けるテキストを含むため、注入文言で @mention を
  抑制されない設計にしている（§5）
- **A-1〜A-6 の定義文を state に同梱する** のが精度の要。定義なしで投げると「publish-sync の 403」の
  ような通常運用の障害まで A と誤判定した（実測）。Jev は字義通りに読むので、境界の定義と除外例
  （「publishAt 自動は A-2 ではない」等）を criteria に書く
- `--self-test`（28 ケース）は Jev を使わず決定論のまま。ただし Jev 分岐（昇格 / 低確信度 / none / 非対称 /
  不正応答 / 環境変数の不正値）は `jev_client._request` をモックしたオフライン 12 ケースで同じコマンド内で検証する。
  `--self-test-jev`（8 ケース）が実 API で言い換え・否定・注入耐性を検証し、`JEV_KEY` が無ければ skip する

**事前検証（本 PR 前のセッションで実測・2026-09-17・`jev-1.13.0`・リポジトリ内では再現しない）**: 既存セルフテスト
28 件を Jev に流した @mention 判定は正規表現と 28/28 一致、正規表現が拾えない言い換え・否定・敵対的注入 10 件は
Jev が 10/10 正解（正規表現は 3/10）。この 38 リクエストの中央値レイテンシ 396 ms、合計コスト約 $0.0015。
このうち言い換え 8 件を `--self-test-jev` に収録した（**リポジトリで再現できるのは 8/8**。`--self-test` の 28 件は
`use_jev=False` で Jev を呼ばない）。

## 4. 下流プロジェクト別の活用パターン（読み替えて使う）

下流はドメインごとに「正規表現やルールで無理をしている意味判断」が違う。以下は本ベースの構成要素と
典型的なプロジェクト種別ごとの候補で、**どれも opt-in の補完として入れ、既存ロジックを残す**（§5）。

### 4.1 本ベースの構成要素で次に候補になる箇所（全下流に共通）

| 箇所 | いま | Jev で補える判断 | 注意 |
|---|---|---|---|
| `discussion_review_trigger.py` / `detect_pr_diff_type.py` | パスと行数で高リスク判定 | 差分の **要約** に対し「認証・権限境界・秘密の扱いに触れるか」を Noul | 差分全文を渡さない（精度低下）。パス規則は残す |
| `code-review` Layer 1 の指摘トリアージ | 敵対的検証サブエージェント | 指摘ごとに「差分の行を根拠に再現可能か」を Noul で前段スクリーニングし、高確信度の PLAUSIBLE を減らす | 最終判定は既存の検証段が持つ。Jev は順位付けまで |
| `user-prompt-submit-guard.sh` の高リスク入力検知 | grep | 「main への直 push / フック無効化 / 秘密の出力を求めているか」を Noul | **フックは同期実行** なので +400 ms とネットワーク依存が毎プロンプトに乗る。無人ルーティンの停止要因になるため、運用実績が出てから |
| `stop-completion-report-check.sh` | 正規表現でテンプレ適合を判定 | 「マージ手順が主役か、アウトカムが主役か」を Score | 同上（Stop フック）。優先度低 |
| スキル / エージェントのルーティング | description の自動マッチ | 「この指示に最適なスキルはどれか」を Choice（候補は installed skills） | 誤ルーティングの影響が小さいので試しやすい |

### 4.2 コンテンツ制作系（記事・動画・ニュースレター等）

- **ファクトチェック・ゲートの前段**: 主張ごとに「出典の記述がこの主張を支持するか」を Noul（公式の
  citation check クックブックと同型）。致命的 NG（A-3）の最終判断は従来どおり人間 / 生成モデルが持つ
- **コメント・問い合わせのトリアージ**: 「技術質問 / 感想 / スパム / 要エスカレーション」を Choice、
  「炎上リスク」を Score。返信文の生成は生成モデルに残す
- **候補の選択**: タイトル案・サムネ文言・投稿時間帯など、生成済み候補から Choice で選ぶ
  （生成させない。候補が state に無いものは選べない点に注意）
- **公開判定の補助**: 「この公開は即時手動公開（A-2）に当たるか」の言い換え検知

### 4.3 開発・運用系（SaaS・内製ツール・インフラ）

- **Issue / PR のルーティング**: 担当領域・優先度・種別ラベルを Choice / Score で提案し、
  `project-manager` が付与する（人間の再ラベルを学習データとして残す）
- **CI 失敗の一次分類**: ログの **抜粋** に対し「環境起因 / テスト自体の不備 / 実装の不具合 / 外部サービス」を
  Choice。`pr-review-watcher` の「flake は根本原因ではない」規律の前段に使う
- **アラートの重複・要対応判定**: 監視通知を「既知の自己回復 / 要調査 / 要人間」で Choice
- **依存更新の影響判定**: changelog の抜粋に対し「破壊的変更を含むか」を Noul（`claude-code-spec-sync` と同型）

### 4.4 データ・リサーチ系（調査レポート・分析パイプライン）

- **収集ソースの関連性フィルタ**: 検索結果ごとに「問いに関連するか」を Noul（RAG パッセージ分類クックブック）
- **要約前の抽出ゲート**: 「一次情報か二次情報か」「日付が明示されているか」を Choice / Noul で分け、
  日付の大小比較はコードで行う（Jev は日付比較が苦手）
- **複合スコアリング**: 「新規性 / 信頼性 / 網羅性」を Score で個別に取り、重み付けはコード側の定数にする
  （重みを変えても再推論不要）

### 4.5 どのパターンでも共通の設計順序

1. **既存のルール判定を残したまま**、Jev の答えを並走させてログに落とす（判定には使わない・シャドー運用）
2. 1〜2 週間分の不一致を人間が見て、Jev を採用する方向（拾う / 落とす）と閾値を決める
3. 採用する方向にだけ Jev を効かせ、閾値は `JEV_*` 環境変数で外出しする
4. セルフテストに「言い換え・否定・注入」の実 API ケースを足し、`JEV_KEY` 無しで skip させる

## 5. 設計ガードレール（全適用箇所で必須）

| # | ルール | 理由 |
|---|---|---|
| G-1 | **opt-in + フォールバック**: `JEV_KEY` 未設定なら呼ばない。呼び出し側は `None` を必ず既存動作に倒し、Jev なしで成立するロジックを残す（§2.1 の契約） | 下流に配布しても挙動を変えない。早期アクセスでレート制限・可用性が変動する |
| G-2 | **非対称**: Jev の判定は「安全側を強める方向」（@mention を増やす・レビューを増やす・エスカレーションを増やす）にだけ使う。ガードを緩める方向（危険操作の検知を外す・レビューを省く）には使わない | 公式が敵対的コンテンツ耐性を改善途上と明記。Issue / PR 本文は外部の誰でも書ける |
| G-3 | **バージョン固定**: `jev-1.13.0` のような固定 ID を使い、`jev-latest` は使わない | エイリアスが動くと閾値の較正が黙って崩れる。レスポンスの `model` をログに残す |
| G-4 | **state は最小限 + 送信前の秘密検知**: 判断に必要な部分だけを名前付きフィールドで渡す。差分・ログは要約 / 抜粋してから。外部由来テキストを渡す経路には `tools/secret_scan.py` の検知器を送信前ゲートとして置き、疑いがあれば送らない（§3 の実装が雛形） | 無関係な情報で精度が落ちる（公式 jaggedness）。秘密・個人情報を state に混ぜない |
| G-5 | **定義を state に同梱**: 境界・除外例を criteria と state に明文化し、質問は 1 判断 1 質問 | 字義通りに読むモデルなので、意図の補完を期待しない |
| G-6 | **計算はコード**: 数値・日付・件数は Jev に聞かず、Jev は意味判断（抽出・分類・程度）だけ | 数値計算・日付比較は苦手と公式が明記 |
| G-7 | **データガバナンス**: 送る内容が第三者（米国ホスト）に渡ることを前提に、下流は自分のデータ方針で採否を決める。ZDR が要るならエンタープライズ契約か不採用 | 学習不使用は明記されているが ZDR は既定ではない |
| G-8 | **フック（同期実行）への組み込みは運用実績が出てから**。無人ルーティンでの停止要因を増やさない | +数百 ms と外部依存が毎回乗る。まずバッチ・ツール側で使う |

## 6. トラブルシューティング

| 症状 | 見るところ |
|---|---|
| Jev が呼ばれていないように見える | `python3 tools/jev_client.py --ping`。未設定なら exit 2、401 なら exit 1。`JEV_DISABLE` が残っていないか |
| 判定が期待と違う | `JEV_VERBOSE=1` で応答を見る。criteria に境界の定義・除外例が書けているか（§5 G-5）。state に無関係な情報が多くないか（G-4） |
| 429 / 529 が続く | 早期アクセスのレート制限変動。クライアントは 1 回だけバックオフ再試行し、それでも失敗なら `None`（既存動作に倒れる）。バッチ処理は 1 リクエストに質問をまとめる |
| 不通なのに処理が遅い | 連続失敗 3 回でサーキットブレーカーが開き以降は即 `None` になる（§2.1）。それでも遅ければ `JEV_TRIAGE_TIMEOUT` を短くする |
| 同じ入力で答えが変わった | `JEV_MODEL` を固定 ID にしているか。レスポンスの `model` を確認する |
