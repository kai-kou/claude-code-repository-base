# セッション完了報告ルール（Completion Report Rules・SSOT）

> **このファイルは「セッション対応が完了したときの、ユーザー向け完了報告の構造」の唯一の正本（SSOT）である。**
> L-052 / L-076 / L-102（`pr-review-flow.md`）がアウトカムの「中身」を規定し、本ファイルが「構造（並び順・何を主役にするか）」を規定する。
>
> **なぜ必要か**（飼い主の明示指摘・2026-06-14）: 完了報告が「PR マージ手順・レビュー往復」を主役にすると、
> ユーザーは「で、何を頼んでたっけ？」とチャット先頭まで遡ることになる。**初回指示の再掲とアウトカムの欠落は報告設計の欠陥**。

---

## 1. 完了報告の必須構造（この並び順で出す）

```markdown
## ✅ 完了報告

**ご依頼**: {セッション開始時の指示を1文で再掲（ユーザーが遡らなくて済むように）}
**できるようになったこと**: {アウトカムを1〜2文。「何ができるようになったか（結果）」を書く}

（必要な場合のみ）**主な変更**: {1〜3行。要点だけ。手順ではなく要点}

---
[PR #{N}]({URL}) / ブランチ `{branch}`  ← 末尾に1行の補足。見出しにしない
```

### 鉄則

1. **冒頭は必ず「ご依頼」の再掲**。これがあるだけでユーザーはチャット先頭まで遡らずに済む（本ルールの最重要目的）。
2. **主役はアウトカム（結果）**。「何をしたか（プロセス）」ではなく「何ができるようになったか」を書く（L-052）。
3. **初回指示に紐づける**（L-076）。PR 対応が長引いても、最終報告は「最初の指示に対して何が達成されたか」で締める。
4. **PR 番号・URL・ブランチ・マージ方法は末尾の補足1行**。主役にしない。URL は必ず Markdown リンク記法（bare URL は L-112 で 404 になる）。
5. **プロセスの詳細は書かない**（L-102 サイレント原則）: レビュー往復・指摘件数・修正サイクル・squash/rebase 等のマージ手順・コミット数は含めない（記録は PR スレッド・Issue コメントに残る）。

### 例（良い例 / 悪い例）

良い例・悪い例の具体テキストは `completion-report-rules-detail.md` を参照（判定ロジックの実体は `stop-completion-report-check.sh` が持つ）。

## 2. Slack 完了通知との関係

`tools/slack_notify.py pr --pr-title "[完了] ..." --outcome "{1文}"` の `--outcome` も本ルールに従う。

- `--outcome` は「初回指示に対して何ができるようになったか」1 文（L-076）。
- プロセス的文言（「マージしました」「PR #N」「〜を更新した」「指摘 N 件対応」等）は入れない。
- `slack_notify.py` は `[完了]` 通知で `--outcome` が空 or プロセス的文言のとき stderr 警告を出す（ハーネスガードレール）。

## 3. 例外（プロセスに触れてよい / 触れるべきケース）

| 事象 | 対応 |
|------|------|
| サーキットブレーカー発動（修正サイクル 2 回超・A-4） | 完了ではなく中断。`problem-investigation-protocol.md` のエスカレーションテンプレートで報告 |
| ファクトチェック致命的 NG（A-3） | 同上。誤りの内容を明示して判断を仰ぐ |
| A-1〜A-6 該当事象 | `user-confirmation-minimization.md` §1 に従い報告 |
| ユーザーが明示的にプロセス詳細を求めた | 求められた範囲で補足する |

上記以外では、完了報告にプロセス詳細を混ぜない。

---

## 3.1 部分納品プロトコル（複数の依頼のうち一部がブロックされたとき）

**依頼が N 件あったら N 件すべてを納品する。** 「半分だけ済ませたもの」「自分の判断でスキップした分を除いたもの」「やり方の報告」は完了ではない。

1 件だけが本当にブロックされている場合は、**残り全件を完了させてから**、ブロック 1 件を **具体的なブロック要因 1 文** で切り出して報告する（何を完了し、何が残ったかを取り違えられない形で書く）。

> 🔴 **A-4 は不変**（本節は修正サイクルの延長を正当化しない）。同一箇所の修正サイクルが **2 回を超えた** 時点で、L-077 の 5 ステップ完了を待たずに §3 の表に従って **中断（エスカレーションテンプレート）へ切り替える**。完了済みの他件がある場合も、報告形式は §3 の中断テンプレートを主とし、完了分は「あわせて完了した範囲」として併記する（本節の通常完了フォーマットは使わない）。

> 🔴 **L-077 は不変**（本節は免罪符にならない）。ブロックを宣言してよいのは `problem-investigation-protocol.md` の 5 ステップを **完全実施してなお自己解決不可** と判定した場合に限る。「さらに調査が必要」「原因は不明」のような **未実施を隠す言い回しは禁止**（それはブロック要因ではなく調査未了の告白であり、書いた時点で 5 ステップに戻る）。書けるのは「◯◯ の API キーがセッション env に未供給で、代替経路も 403（A-6）」のように、**ユーザーだけが動かせる一点** を名指しした 1 文だけ。

## 4. 完了・成功の定義

- [ ] 冒頭に「ご依頼（初回指示の再掲）」がある
- [ ] アウトカムが主役で、プロセス（マージ手順・レビュー往復）が主役になっていない
- [ ] PR 番号・URL・ブランチが末尾の補足 1 行に収まり、Markdown リンク記法になっている
- [ ] Slack `--outcome` も初回指示アウトカム 1 文になっている
- [ ] 依頼が複数件あった場合、**完了分が全件納品され**、未完了分はブロック要因 1 文で名指しされている（§3.1）
